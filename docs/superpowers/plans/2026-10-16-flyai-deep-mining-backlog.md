## 2. 待定方向明细

### 2.1 A2 — `extra` 字段定向解析（零新增调用，纯挖潜）

- **做什么**：酒店条目的评分/位置/距 POI 距离、POI 条目的 30+ 分类等级（国家级/省级文保单位）从 `extra` 提升为结构化字段；POI 分级直接喂 proposal 的"田野点背景"章节。
- **价值**：文保分级是学术叙事里天然的田野点重要性佐证（"调研点含 2 处国家级文保"）；零调用成本，纯解析增强。
- **依赖与耦合**：与 M1 spike 同源——spike 核验航班响应形态时**顺带核验酒店/POI 的真实字段名**，结论直接决定本条的字段映射表；M1 落地后 `SearchItem` 已有 `schedule` 先例，本条照葫芦画瓢加结构化字段。
- **工作量**：S（解析 + 字段映射 + 测试，约 1 个任务）。
- **建议时机**：M1 落地后随时可做；比赛前可作为低风险的加分补充。

### 2.2 A3 — `jump_url`/`pic_url` 进交付物

- **状态**：2026-10-18 调研完成并经用户裁决——与 D11 合并为「方案 B」立项实施（spec 见 `docs/superpowers/specs/2026-10-18-fliggy-booking-link-design.md`）。
- **做什么**：行程表附可点预订链接、proposal 附录附住宿图片。
- **价值**：交付物从"报告"变"可执行文件"；答辩演示时点击即达。
- **依赖与耦合**：~~价格标注查询时戳~~——该子项**已被 M3 吸收**（`BudgetItem.source` 格式 `"flyai 快照 sc_xxx（2026-10-16 查询）"`）；本条剩余部分依赖 M3 的快照结构稳定（链接时效同样需要时戳语义）。M1-M3 已落地并过终审，依赖已解除。
- **2026-10-18 调研结论**：
  1. FlyAI 8 原语全为搜索类，**无任何下单/交易 API**；「跳转下单」唯一合规通道 = 搜索结果自带 `detailUrl`（飞猪 H5 预订页，实测样本 `router.feizhu.com/multi/webview?url=...`）透传到交付物；
  2. kernel 断点定位：`SearchItem.jump_url` 已归一化（flyai.py `_JUMP_KEYS=(jumpUrl,detailUrl)`）、快照落盘已保留，但行程聚合 `_candidates()`（itinerary.py L165-170）丢弃 jump_url，`ItineraryPlan` 与前端行程卡/导出物均无链接；
  3. 正式 API Key 下商品链接自动带推广者佣金归因（响应含 `commissionMoneyYuan` 字段），无需改造链接；体验模式无归因、价格脱敏（"¥1xx"）、flight 系统性业务失败（与 spike A1 双证）；
  4. 交通类（机票/火车）深层结构无链接字段且推广者计划暂不分佣 → 现阶段仅住宿条目可跳转，交通条目如实无入口。
- **工作量**：S-M（kernel 侧小改，proposal/前端渲染中等）。
- **建议时机**：~~M3 落地后~~ → 已立项（见状态行）。

### 2.3 B6 — itinerary 腿级 AI 兜底

- **依赖与耦合**：独立于当前批次；但可复用 M2 沉淀的"llm 注入 + 失败降级"模式。
- **工作量**：S（策略函数 + 测试）。
- **建议时机**：随时（无阻塞依赖）。

### 2.4 C7 — `search_ai` 田野意图查询模板库

- **做什么**：site_profile 现在的 `search_ai` 只有固定 query（"适合长期驻村的便宜住宿 民宿 招待所"）；改为按研究主题 × 场景（宗教/市场/生态/都市）由 LLM 动态生成语义查询。
- **价值**：`search_ai` 是飞猪 8 原语里的"杀手锏"，场景化深化直接强化说明书创新点 1（工具非消费场景使用）的叙事层。
- **依赖与耦合**：独立；与 M2 的 LLM 节庆抽取共用"llm slot 注入 + 降级"骨架。
- **工作量**：M（prompt 设计 + 主题→query 生成 + site_profile 接线 + 测试）。
- **建议时机**：**赛前冲刺首选**——若 M1-M3 提前完成且有余量，本条叙事收益/工作量比最高。

### 2.5 C9 — 海外行前手续清单

- **做什么**：签证/保险/租车/疫苗的 `search_keyword` 结果自动汇成 proposal"行前准备"章节，与既有二段式海外保障策略（枢纽城市 + 学术接待方）形成闭环。
- **价值**：海外场景答辩 demo 的完整性；proposal 章节从模板生成升级为数据驱动。
- **依赖与耦合**：依赖 M3 的 proposal 接线模式（context_block 携带，不改 documents 内部结构）；keyword 结果质量需先小规模核验（可并入 M1 spike 的节庆查询同场验证）。
- **工作量**：M（keyword 采集 + 章节生成 + 测试）。
- **建议时机**：M2/M3 之后。

- **做什么**：
  1. 通用缓存/速率控制——防宿主 Agent 循环打爆飞猪 CLI（M2 的 `MAX_SAMPLES=16` 硬顶只覆盖时窗能力自身，不覆盖宿主循环失控场景）；
  2. 体验模式能力矩阵展示——前端明示哪些能力在无 Key/体验模式下可用；
  3. 真实响应 fixture 录制——**已被 M1 吸收**（spike 真实响应脱敏进 `tests/fixtures/flyai_responses/`），本子项关闭。

- **依赖与耦合**：速率控制与 M2 采样策略互补；能力矩阵依赖体验模式透传（M1 §3.3）落地后才有数据源。
- **工作量**：M。
- **建议时机**：赛后产品化阶段；速率控制若 CI/演示中出现限流再提前。

### 2.8 终审回填 — 时窗批次 final review 裁决项（F13/F14）

> 来源：2026-10-16 时窗分析批次（M1-M3）整分支终审（REQUEST_CHANGES → ONE fix → APPROVED）的裁决回填，非方向地图原始条目；编号 F13/F14 为回填序号，不与 A-E 混排。

#### F13 — MCP tools content 附 snapshot_ids（原 spec §5.2 条目，descope）

- **做什么**：MCP Server 的 tools 返回 content 附 `snapshot_ids` 字段，供 MCP 客户端追溯预算证据快照。
- **价值**：MCP 消费侧与 web 前端（SnapshotDisclosure）的证据链对称性。
- **依赖与耦合**：前置是 MCP 侧先有快照消费方——需暴露快照查询面（如 resources `searches://{cid}` 或专用 tool）。当前快照经 web 宿主 REST 端点披露，MCP 客户端拿到 ids 也无查询渠道，纯附字段无意义（终审裁决理由，spec §5.2 已注 descope）。
- **工作量**：M（MCP resources/tools 扩展 + 快照只读接线 + 契约测试）。
- **建议时机**：出现真实 MCP 快照消费场景（外部 Agent 经 MCP 集成田野罗盘并要求证据追溯）再做。

#### F14 — 缓存命中复用（终审 Obs-5，原 spec §5.2 “可先”项）

- **做什么**：二次生成 proposal 前宿主先 `list_cached_searches` 按 query 精确匹配，命中即复用快照，减少重复飞猪调用。
- **价值**：省调用成本 + 防限流；同 query 同证据的快照语义一致性（复用不改变包络数据本身，spec 原口径）。
- **依赖与耦合**：query 序列化格式需稳定（`time_window::{dest}` 等落盘格式已定）；宿主侧独立改动，不动 kernel。
- **工作量**：S（查表 + 精确匹配 + 测试）。
- **建议时机**：随时；演示/CI 中出现限流再提前。
