# 田野罗盘项目规划审阅意见

- 审阅日期：2026-10-14
- 状态：审阅建议，待纳入设计与实施计划；本文不代表相关改动已完成
- 审阅方式：规划文档与当前代码静态对照，未运行测试、未核验外部服务能力或申请规范
- 目的：保留现有架构方向，补齐影响方案可信度与运行可靠性的契约，调整实施顺序

## 1. 总体判断

方向值得继续，架构基本合理，但还需要补上关键契约，才能作为可靠的实施依据。当前最需要优先处理的是行程与预算可信度、用户确认语义和回合恢复机制。

建议首版围绕“可核验的田野筹备方案”形成完整闭环：研究描述 → 田野点画像 → 行程与预算 → 用户确认 → 方案导出。研究方案作为辅助草稿提供，申请体例支持范围要明确。

### 值得保留的设计

1. **共享能力内核、双宿主接入。** Web 进程内直接调用内核，MCP 服务供外部 Agent 复用，避免让自建 Web 为协议层承担额外复杂度。
2. **结构化工具数据直接驱动界面。** 价格与预算卡片以工具结果为来源，减少模型转述造成的数字失真。
3. **渐进迁移、显式降级、分层测试。** 利用现有 CLI 与测试资产，逐步迁移；依赖不可用时展示能力限制。

## 3. R1：明确首版交付物与体例支持范围

### 发现

总体设计已经将当前重心定位为行程与田野保障，但 README 和当前生成提示词仍包含“符合基金委标准”等表述。开题与基金模式暂时回退通用八章结构，容易让用户将草稿理解为可以直接提交的申请材料。

当前 `ResearchContext` 也尚未包含计划要求的 `purpose` 字段，用途采集与模式选择尚未形成一致契约。

### 建议

- 首版交付物明确为田野筹备方案，包含选点依据、进入田野安排、访谈对象建议、行程、预算、风险与待核实事项。
- 研究方案明确标注为辅助草稿；开题、基金体例尚未实现时，在选择用途或生成前说明，不只在文末附注。
- 区分请求体例与实际生成体例，例如 `requested_mode`、`effective_mode`，避免回退后仍被界面当作目标体例。
- 统一用途字段、允许值和用途到体例的映射；课程用途的处理也应明确。
- 参考文献只使用可追溯的已有资料。缺少材料时留空或列出检索需求，不由模型补造引用。

### 验收条件

- README、界面、提示词、导出文件与参赛说明对能力支持范围表述一致。
- 选择未支持体例时，用户在生成前能看到限制，导出文件也标注实际体例。
- 无文献输入的场景不产生虚构参考文献。

## 4. R2：预算表达必须反映数据完整性

### 发现

当前行程代码在交通或住宿缺报价时跳过相应预算条目，同时仍生成总额与 `over_budget`。因此“已知费用未超支”可能被展示为“完整方案在预算内”。

住宿按晚价乘夜数计算，缺少房间数或入住安排参数；餐饮与市内交通按总预算的 15% 估算。后者随用户预算变化，并不反映人数、天数或目的地成本。搜索结果进入行程候选时，还会丢失部分原始价格和来源信息。

### 建议

- 预算条目记录币种、计价单位、数量、人数或房间数、报价时间和来源引用。
- 分别展示已知费用小计、估算费用、未覆盖费用；增加预算完整性状态，例如 `complete / partial / unknown`。
- 缺关键报价时，只能判断已知小计是否超支；不能据此宣布完整方案预算充足。
- 将餐饮、市内交通等估算改为可解释、可调整的数量与单价模型，并明确哪些费用尚未覆盖。
- 长住酒店日价只能作为住宿线索或估算依据；未确认长期可订和计价口径时，不宣称已经验证长期住宿成本。
- 交通选择同时考虑时间、换乘、抵达条件和进入田野安排，最低价仅作为排序因素。
- 缓冲日进入实际日历分配，明确其是否包含在总天数内；多点移动时间与调研时间不得重复占用。

### 验收条件

- 多人行程的住宿费用具有明确入住假设，数量可复核。
- 任一关键交通或住宿报价未知时，界面显示“预算不完整”，并列出未覆盖项。
- 每个计入预算的搜索报价能追溯到来源和时间；估算条目有独立标签。
- 行程各时间段与缓冲安排符合总天数约束。

## 5. R3：阶段推进需要用户确认与依赖失效机制

### 发现

计划与当前代码均采用定位字段计数推进；行程阶段依赖 `has_itinerary`，方案阶段依赖 `has_proposal`。这些条件证明数据或产物存在，不能证明研究者认可。

当前 B→C 要求至少一个访谈对象，尚未定义非访谈型研究的跳过路径。

### 建议

- 区分信息齐备、草稿已生成和用户已确认。允许先探索、再补资料，不将每一步都变成审批；但最终方案应有明确确认状态。
- 将用途、研究问题、时间、规模等核心字段的必需性写清楚，避免任意字段计数替代业务条件。
- 允许返回前阶段修改。日期、地点、人数等关键输入变化时，将依赖的行程、预算和提案标记为需要重新核验。
- 保存确认记录及其对应输入版本，避免旧确认被沿用于已改变的方案。
- 支持研究方法适配：非访谈型研究可记录“不适用”及理由，不强制添加访谈对象。

### 验收条件

- 草稿生成不会自动等同于用户确认或项目完成。
- 修改出行日期后，旧行程与预算不再显示为已确认的当前结果。
- 非访谈型研究可以完成整个筹备流程。

## 6. R4：先定义回合生命周期，再实现 SSE 重连

### 发现

前端计划要求断线后使用 `Last-Event-ID` 重连 POST 并补发，但未明确如何定位原回合、如何防止再次执行工具、事件保留多久、进程重启后如何恢复。

仅按 `call_id` 覆盖工具卡片不能防止 `message_delta` 重复追加。取消接口中的消息 ID 获取时机，以及取消后仍在运行的子进程结果如何处理，也需要契约。

### 建议

- 将创建回合与订阅事件分开；创建动作返回 `turn_id`，事件订阅绑定该回合。若保留 POST 流式接口，也必须定义等效幂等与恢复语义。
- 请求携带幂等键；重复提交或重连返回原回合，不重复执行工具。
- 每条事件包含回合标识与单调事件序号；前端对全部事件去重，而不仅是工具结果。
- 定义 `running / completed / failed / cancelled` 等状态及唯一终止结果；给出事件保留期限和回放过期后的恢复方式。
- 用户消息、工具结果和状态变化及时持久化，避免全部等到轮末才保存；明确事件发布与落盘顺序。
- 定义取消语义：停止后续模型和工具调度；已经启动的调用能否中止、迟到结果是否保存，必须一致。
- 至少约束同一项目同时只有一个写回合；MCP 与 Web 并存时明确写入协调方式。

### 验收条件

- 断线重连后，工具只执行一次，正文与卡片均不重复。
- 刷新页面可以恢复项目与回合状态。
- 取消回合有明确终止事件，迟到结果不会把回合重新变成完成态。
- 若首版不支持进程重启后继续执行，应将遗留回合标为中断，并提供明确恢复路径。

## 7. R5：统一架构边界与能力契约

### 发现

总体设计规定 LLM 只出现在内核 `documents/` 和宿主 Agent Loop；内核实施计划却将调用 LLM 的共享循环放在 `kernel/loop.py`，两者冲突。

计划要求统一 `Envelope`，当前文档能力仍分别返回 `ProposalDoc` 或字典；实施计划还要求直接将工具结果 JSON 截为 2000 字符，可能得到不完整的结构与误导性摘要。

### 建议

- 将共享循环放到独立运行时模块，由 CLI、Web 复用；内核保留能力、数据模型与纯判定逻辑。
- 将“无状态”准确表述为“不隐式读取或写入项目状态”。搜索与生成依然依赖外部服务，不应被误解为纯函数。
- 明确统一包络由能力入口还是宿主适配层负责；保证 MCP、Web 与 CLI 在成功、失败和降级时语义一致。
- 用结构化摘要替代直接截断 JSON，保留条目数量、关键数据、完整性状态及完整结果引用。
- 定义并行规则：只读独立调用可并行，存在依赖或写状态的操作按顺序执行；限制整回合的时间、工具调用数与费用，不能只限制模型迭代数。
- 从同一份契约生成或校验前端类型，减少手工镜像模型造成的漂移。

### 验收条件

- 总体设计与实施计划对共享循环位置、依赖方向和 LLM 使用位置一致。
- 文档能力的降级状态能通过结构化数据传到界面。
- 工具摘要保持合法结构，完整结果可访问。
- 宿主契约测试验证实际输入输出与行为，不仅比较 schema 或 description。

## 8. R6：验收从流程跑通提升到方案可用

现有 L1—L4 与真实模型评估集应保留。补充以下案例，防止只验证“八章可见”“数字与 mock 相同”，却遗漏业务错误。

| 场景 | 核心验收要求 |
| --- | --- |
| 三个月驻村，但只有短住酒店报价 | 长住费用标为估算或待核验，不宣称长期住宿已落实 |
| 多人、多点行程，部分费用未知 | 数量口径明确，预算不完整可见，各腿与夜数一致 |
| 用户修改已确认日期 | 相关行程、预算、提案失效状态正确 |
| SSE 断线重连、重复事件 | 工具只执行一次，正文和卡片无重复 |
| 取消时工具仍在执行 | 状态终止明确，迟到结果按约定处理 |
| 无文献材料 | 不生成虚构引用，明确资料缺口 |
| 非访谈型研究 | 可跳过访谈对象登记并完成流程 |
| 体验模式价格脱敏或源失败 | 不将未知报价当作零元，降级原因可见 |
| 偏远田野点缺少平台供给 | 区分已搜索到的枢纽方案与尚待联系的当地接待安排 |

CI 使用确定性 fixture 和 fake LLM 验证契约；发布前及提示词、模型配置变化后，用真实链路回归行为评估集。人工复核重点是选点理由、方法匹配、预算完整性、伦理建议与来源可追溯性。

## 9. 建议实施顺序

### 第一阶段：补齐契约

先统一用途与输出体例、预算完整性、确认与版本失效规则、返回包络、回合与事件协议，修正总体设计和实施计划的冲突。此阶段完成后再接入 Web 与前端业务状态。

### 第二阶段：贯通一个真实闭环

实现一个田野点的筹备流程：研究描述 → 画像 → 可复核行程与预算 → 用户确认 → 导出。同步验证无 key、无报价、修改日期、断线恢复等路径。

仓储先满足项目与回合的一致性需求；若 JSON 无法可靠承担事件恢复与写入协调，提前落地最小 SQLite 实现，不必等待完整存储扩展计划。

### 第三阶段：扩展接入与界面

闭环稳定后完善 MCP 全工具接入、SQLite 存量迁移、完整移动端与更多输出体例。前端视觉方向可保留，但界面和卡片应先服务于业务状态表达。
